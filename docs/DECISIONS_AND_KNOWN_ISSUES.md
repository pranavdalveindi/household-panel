# Decisions and Known Issues

## Decisions evident from implementation
- **Next.js App Router:** pages and API handlers are colocated under `app/`.
- **Supabase Auth:** password-based sign-in and admin user lifecycle use Supabase Auth.
- **Application roles in `user_roles`:** roles are stored separately from Auth accounts.
- **Company email restriction:** application flows check `@inditronics.com`.
- **Privileged server-side data access:** admin client is used for user administration and several household/appointment operations.
- **Separate workflow statuses:** `call_status`, `appointment_call_status`, and `installation_status` represent different stages.
- **Multiple appointment records:** appointment dates are stored separately in `household_appointments`, rather than one date field alone.
- **Status normalization:** household PATCH route trims and case-normalizes supplied status strings.

## Confirmed implementation observations
1. No database migrations/schema dump are included in the supplied archive; reproducible database setup cannot be established from this repository alone.
2. No test files or `test` package script were found.
3. `app/layout.tsx` still uses default Create Next App metadata (`Create Next App`, `Generated by create next app`).
4. Login domain validation is client-side, while API handlers repeat domain checks where they handle protected data. Server-side route checks remain essential.
5. `GET /api/households/:id/appointments` authorizes by authenticated session and company domain, but does not check a particular application role.
6. Appointment deletion route receives both household `id` and `appointmentId`, but the delete query visibly filters only by appointment `id`; verify parent-child scoping.
7. The admin client uses a service-role/secret key and bypasses user-scoped policies; every privileged handler must reliably enforce authorization.
8. No automated tests, CI pipeline, or deployment manifest is included in the archive.

## Potential risks / NEEDS VERIFICATION
- **RLS and database policies:** unknown because schema/policies are absent. Verify in Supabase and do not assume the service-role client is protected by RLS.
- **Appointment ownership/parent scoping:** deletion should likely confirm `household_record_id` matches the path household ID.
- **Appointment workflow race conditions:** creation checks `appointment_call_status` then inserts in separate operations; a concurrent status change could occur between them.
- **Future appointment rule:** UI label says future date/time, but API validates parseability, not that the timestamp is in the future.
- **Household PATCH constraints:** inspect the complete handler and validate every transition on the server, including whether `appointment_call_status` can be set to `Scheduled` when call status is not successful and whether a rejected status can later be changed.
- **Admin role protection:** review exact conditions for changing/demoting/deleting administrators and confirm the last-admin case is handled.
- **User deletion and role records:** verify foreign keys/on-delete behavior for `user_roles` and `household_appointments.created_by`.
- **Sensitive error messages:** some admin handlers return provider error messages to the client. Consider returning stable public errors while retaining server logs.
- **Status vocabulary consistency:** UI/API strings use mixed capitalization and wording (`call successful`, `Not reachable`, `Number does not connect`). Confirm these match existing database values and any imports/reporting.
- **Accessibility and usability:** verify table interactions and error handling on mobile and with keyboard/screen readers.
